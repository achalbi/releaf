What changed, what stayed

The proposal is a layout swap, not a behavior swap. The host (ModalBottomSheet), the entry point (FAB tap from the BottomNav center slot), the cream canvas, the 20dp top corners, the drag handle, the "what arrived?" eyebrow + serif title pair, and the calendar-toggle pill in the top-right all stay verbatim. The mode-row composable becomes a tile composable; the CaptureMode enum is what gets pruned.

What got dropped from the mode set

Overview. Removed. Overview isn't a capture — it's the read-only summary tab inside the page-detail editor (per CaptureMode.kt's own comment). Letting it sit in the Quick Capture sheet conflates "capture a thing" with "look at all the things." The page-detail screen still uses the full enum unchanged.

Contact and Location. Removed from quick capture, kept as inline inserts inside the NotepadEntry / Page editor where they're already first-class JSON columns. They're context operations on an entry, not standalone captures — adding a contact "to today's log" without a surrounding entry is a weak interaction. The schema change is zero; only the entry surface for these two moves.

To-do. Removed from quick capture, kept as the first-line behavior inside the Note tile. Typing - [ ] something in the note editor (markdown autocomplete) creates a to-do item; typing plain text creates a note. One tile, two modes based on what the user types. This matches the existing todo_lists data model — todos are already entry-attached, never standalone.

What got added

Note. Text capture didn't exist as a mode in CaptureMode because text goes into notepad_entries.notes, not captures. But it's the highest-frequency capture in any daily-journal app. Adding it as a tile (with keyboard-up affordance) is what makes the sheet actually useful for the most common case. Implementation: tile tap opens the sheet's text-input mode (no separate screen on the happy path).

From clipboard. Conditional tile, only painted when the system clipboard contains a URL or recognizable rich payload. Renders coral so it reads as the "do this now" tile. Tap commits a reference_links row with the clipboard URL pre-filled and OG metadata fetched in the background. Long-press lets the user re-target it. When the clipboard is empty or unrecognized, the slot collapses and the grid becomes 5 tiles in a 3 + 2 layout.

Open questions

1 · Do we keep the calendar-toggle pill?
The existing sheet has a calendar pill that expands an inline panchanga calendar. I preserved it in mock B, but a tile grid + an inline calendar panel makes the sheet visually heavy. Recommend: keep the pill, expand to full-screen calendar route on tap (instead of inline expand) — see CalendarPanel already wired up.
2 · 3 columns or 2 columns?
The reference image is 3 columns. A 2-column 3-row layout has bigger tap targets but forces more scroll on the small phone heights we already worry about (iPhone 13 mini). Recommend: 3 columns at 390 dp width; revisit at iPhone SE width where 3 columns make tile labels uncomfortably narrow.
3 · Where does the "Capture into…" picker live?
Long-press a tile → secondary sheet asking which parent. That's an extra modal stacked on a modal, which iOS handles fine but Android often doesn't (the bottom-sheet-on-bottom-sheet pattern is fragile in compose-foundation 1.7.x). Recommend: on long-press, swap the tile grid in place with an "into…" target list (Today · Yesterday · Specific page · Pick later) — single sheet, no nested modal.
4 · Should the FAB long-press for voice happen here or be a follow-up?
The FAB long-press is the spec's most novel gesture and the riskiest UX claim — see DAILY_CAPTURE_UX.md §2.4. It's orthogonal to the sheet redesign. Recommend: ship the tile grid first (lower risk, smaller diff), then layer the long-press in a follow-up so each can be evaluated independently.
5 · How do we reach the dropped modes (Contact, Location, To-do, Overview)?
Contact and Location move inline into the NotepadEntry / Page editor — the editor already has the JSON columns and shows them as collapsed sections. To-do becomes implicit through the Note tile via markdown. Overview is reachable from the page-detail tab bar, unchanged. Confirm: none of these reductions cost a real user-flow path, they just relocate the entry point closer to the surface that actually uses the data.

Implementation footprint (Android)

One file changes meaningfully: QuickCaptureSheet.kt. The CaptureRow composable becomes CaptureTile; the LazyColumn becomes a LazyVerticalGrid(GridCells.Fixed(3)) or a hand-rolled 2×3 with FlowRow. CaptureMode.kt gains a Note entry (text) and the page-detail tab bar continues to use the full set. QuickCaptureSheetHost signature is unchanged. iOS needs the parallel change in QuickCaptureSheet.swift — same shape, LazyVGrid with GridItem(.flexible(), count: 3). No schema migration; no nav graph change.
