What changes when Capture becomes a page

The visual content stays nearly identical to v6. The bigger shifts are architectural — Capture moves from a transient modal to a destination with identity, state, and a route. That has real consequences worth pulling apart.

The height surprise

Going from modal to page doesn't actually buy more vertical room. The modal was hiding ~70 px of Home above (sheet started at top=70) and showing the BottomNav was either inside the sheet's chrome or hidden. The page version shows the BottomNav (~76 px) plus the page header (~62 px) and the status bar (~36 px), leaving ~670 px of body content. That's roughly the same as v6's modal (~750 px sheet, but with the title block + drag handle eating some of that).

So v7's body still uses the same compression strategy as v5/v6: chip-row pre-tags, 1.05:1 capture tiles. The Scan hero stays at full size. Everything fits without internal scroll on a 390×844 phone.

What this resolves

Persistent Day/Recents state. A user who flips to Recents to check what they last captured, then goes elsewhere and comes back, sees Recents still selected. With the modal, every dismiss reset the state to Day.

Deep linking. releaf://capture, releaf://capture?kind=photo, and releaf://capture?tag=letter all become trivial because Capture is now a real route. The modal version had to be triggered after cold-launching into Home, which is a fragile dance.

Modal-on-modal fragility. v1's open question 3 worried about opening a "Capture into…" sheet on long-press from inside the modal sheet — because Android's compose-foundation 1.7.x has a real bug stacking sheets. v7 makes it a non-issue: long-press opens a sub-sheet on top of a regular page, which works.

Conceptual ambiguity of the FAB. The center "Leaf" was always a weird hybrid — it lived in the BottomNav slot but didn't own a destination. Promoting it to a real tab makes the slot consistent with Home / Notebook / Notepad / Settings.

What this costs

Capture is no longer a "quick" gesture. Tapping FAB → sheet felt lightweight, dismissible. Tapping FAB → tab navigation feels like switching context. For users who think of capture as "interrupt my current screen to add something," the modal idiom matched their mental model better.

Mitigation: the Hold the green Leaf button to record voice without opening this tab footer survives. Voice — the highest-frequency quick capture — still works as a gesture from anywhere via the FAB long-press. Photo / Scan / Note all still go through the tab, but those are deliberate captures anyway.

NAV_GRAPH.md changes required

The current docs/NAV_GRAPH.md lists quick_capture as a "Modal" kind hosted under any tab. v7 changes it to a "Top-level" kind with route id capture (or keeps quick_capture as the route name; either is fine). The five-tab BottomNav already has Leaf in the center slot — it's already visible, just gains a real destination behind it. The deep-link table updates: releaf://capture goes from "open modal" to "select Leaf tab"; releaf://capture?kind=photo goes from "open modal with kind preset" to "select Leaf tab + open the Photo tile flow."

Open questions

1 · Should Capture be the cold-launch landing for some users?
The launcher continue-scope already has a setting for "what happens on app icon tap" (per DAILY_CAPTURE_UX.md). Adding "land on Capture tab" as a fourth value (today / append_to_latest / new_shell / capture_tab) lets capture-first users skip the Home detour entirely. Recommend: ship without it; add if usage data shows users immediately tapping FAB after cold-launch >50% of the time.
2 · Does the Capture tab show below-the-fold content if the user scrolls?
v7 fits all six tiles + the hero in one viewport. But unlike a modal, a page naturally invites scroll. Adding a "Recent captures" section below the tiles (last 3 captures across all kinds) gives the page more substance without hurting the above-the-fold flow. Recommend: add the recent-captures strip in a follow-up; ship the same v6 content for v1.
3 · How does "back" work from a Capture sub-flow?
Tap Photo tile → camera opens. Cancel → back to Capture tab? Or back to the previous tab the user was on? Recommend: back to Capture tab, since that's where the action started. The Capture tab itself doesn't have a back button (it's a top-level destination); pressing system back from Capture returns to the previously-active tab.
4 · Does the FAB visual change need a token?
The "active tab" treatment is a cream ring + coral outline around the coral FAB. Add it as color.nav.fabActiveRing in design-tokens.json alongside the existing shadow.fab. It's effectively a new visual state for the FAB; doesn't affect any other component.

Implementation footprint

More substantial than previous iterations because the navigation shape changes. Android — add a CaptureScreen.kt under features/capture/ with the same body content as the v6 sheet. Update the NavHost in the app shell to add a capture top-level destination. The BottomNav already has Leaf in the center slot; gate its onClick from openSheet() to navController.navigate("capture"). Delete QuickCaptureSheet.kt's ModalBottomSheet wrapper (keep the row composables, they'll live on the page). iOS mirrors — new CaptureView.swift, tab item added to MainShell, no more .sheet presentation. Routes — update docs/NAV_GRAPH.md per above. No SQL migration; pre-tag still rides existing tags.
